# Trim 迭代的 CUDA 加速计划：计算什么、如何并行、何时同步

本文依据当前 DEL 源码制定改造计划。**这是一份实现计划，尚未实现 CUDA 后端，也没有实测 GPU 加速比。** 入门背景可先看 [trim 更新的浅显解释](trim_update_beginner_zh.md)。

推荐路线是：**保持现有计算规则，将“边上的距离与导数计算”和“节点上的梯度汇总与坐标更新”放到 GPU；用独立的旧坐标、候选坐标和当前坐标数组，保证一次更新读取的是同一份状态。停滞跳跃先保留 CPU 对照实现，再迁移为“连通分量之间并行、分量内部按原边顺序处理”。**

难点并不是距离公式，而是三件事：一个 trim 可能受多条边影响；候选更新可能被回退；跳跃修复存在执行顺序。

阅读顺序建议：先看第 2 节流程图和第 5.6 节的双 trim 算例，再看第 4 节核函数表、第 6 节同步和第 7 节跳跃。开始编码时按第 13 节分阶段实施。

## 1. 先明确 GPU 实际上要更新什么

### 1.1 输入仍然可以理解为当前 trim 的坐标

对于水平布线层，每个 trim 只沿 x 方向滑动，y 不变；对于垂直布线层，交换 x、y 的角色。因此，每个 trim 在迭代中只需要一个变化量。

以水平层为例：

$$
x_i=x_{i,0}+W u_i,\qquad y_i=y_{i,0}.
$$

- $i$：一个 trim 的编号，同时也是图中的节点编号。
- $x_{i,0},y_{i,0}$：这个 trim 的原始中心坐标，单位为 DBU，即数据库坐标单位。
- $x_i,y_i$：当前中心坐标，单位也是 DBU。
- $W$：当前层的线宽，单位为 DBU。
- $u_i$：相对原始位置的**累计位移除以线宽**，没有单位。源码中的名字是 positions_。

例如原始 x 为 100、线宽 W 为 10、当前 u 为 0.2，则当前 x 为 102。**u 不是绝对坐标，也不是这一轮的移动量。** 如果要从已有当前坐标开始，先用“当前坐标减原始坐标，再除以 W”转换成 u；现在的实现则从所有 u 等于零开始。

GPU 首版继续使用这种表示，以便与 CPU 对照。CPU 保留原始的双倍整数中心坐标，避免丢失半 DBU 的原点；迭代数组使用 double。

源码：[初始化](../src/optimize/Optimizer.cpp)，LayerOptimizer 构造函数，第 45–86 行；[节点坐标表示](../include/del/Graph.h)，Vnode、along2。

### 1.2 一条边负责计算两个 trim 之间的有向距离

$$
d_e=d_{e,0}+u_t-u_s.
$$

- $e$：一条约束边。
- $s,t$：这条边的起点 trim 和终点 trim，对应 src、dst。
- $d_{e,0}$：两端原始中心沿可移动方向的坐标差，除以 W；初始化时计算一次。
- $u_s,u_t$：两端当前累计归一化位移。
- $d_e$：当前的归一化有向距离，可能为负数；不是二维欧氏距离。

如果原始 x 分别为 100、140，W 为 10，则初始距离是 4。后来两端分别移动 −1 DBU、+1 DBU，u 分别为 −0.1、+0.1，距离就变成 4.2。

源码：[Optimizer.cpp](../src/optimize/Optimizer.cpp)，arcDistance，第 203–209 行。

### 1.3 “计算梯度再更新”，在 GPU 上就是三件事

1. **每条边独立算**：当前距离、规则惩罚值、惩罚对距离的导数。
2. **每个 trim 独立汇总**：收集它连接的所有边带来的梯度，再算自己的移动方向。
3. **每个 trim 独立生成候选位置**：全部使用本轮开始的坐标；检查整层能量后，一起接受或一起放弃。

这里“独立”指同一阶段内的并行。阶段之间仍然要按顺序执行。

## 2. 一轮迭代的完整 CUDA 执行顺序

下面先讨论一层。每层的线宽、能量、步长和接受条件都独立计算。

~~~mermaid
flowchart TD
    A["保存本轮开始坐标 u_prev"] --> B["每条边：距离、惩罚、导数"]
    B --> C["每个 trim：汇总梯度、计算方向"]
    C --> D["整层归约：旧能量、最大方向幅度"]
    D --> E["每个 trim：从 u_prev 生成候选 u_trial"]
    E --> F["计算候选能量和移动数量"]
    F --> G{"候选被接受？"}
    G -- 是 --> H["整体提交到 u_current"]
    G -- 否且还能重试 --> I["缩小步长或换扰动"]
    I --> E
    G -- 重试结束 --> J["u_current 保持本轮开始的位置"]
    H --> K["并行更新所有边的停滞计数"]
    J --> K
    K --> L["处理停滞跳跃：分量间并行，分量内有序"]
    L --> M["最终统计、必要时回传坐标"]
    M --> N["下一轮"]
~~~

**每次回溯都从 u_prev 重新生成候选，不能从上一个失败候选继续走。** 跳跃是在梯度尝试结束后执行的额外步骤，不进入这轮梯度回溯。

## 3. 显存中需要放哪些数据

### 3.1 初始化一次的静态数据

将现有嵌套 vector 整理成连续数组，GPU 不直接访问 OpenDB、STL 容器或 GUI 对象。

| 数组或数据 | 长度 | 含义 |
|---|---:|---|
| low、up | N | 每个节点允许的归一化累计位移范围；blocked 节点均为零 |
| degree | N | **1 加上关联边数**，不是单纯的图论度数 |
| original_node_id | N | 原始层内节点编号，供扰动奇偶判断使用 |
| src、dst | E | 每条边的两端节点编号 |
| initial_distance | E | 原始归一化距离 |
| arc_type | E | A、B 或 C 规则类型 |
| range_offsets、range_low、range_high、边界标志 | 按实际区间数 | 每条边合法区间的连续存储，用于违规判断 |
| incident_offsets、incident_edges、incident_sign | N+1、2E、2E | 节点关联边的 CSR 邻接表；符号表示起点取负、终点取正 |
| component_offsets、component_edges | 按分量/边数 | 跳跃阶段使用的连通分量边列表 |
| 每层参数 | 每层一份 | W、三种规则阈值、修复容差、跳跃偏移、最大梯度步长 |

N 是节点数，E 是边数。CSR 的含义很简单：节点 i 的关联边，存放在 incident_edges 中从 incident_offsets[i] 到 incident_offsets[i+1] 之前的那一段。

每个节点的关联边必须按原始边顺序排列；每个分量的边也按原始边顺序排列。重新排列内存时保留原节点编号，不能用重排后的编号决定扰动方向。

合法区间与光滑惩罚是两个概念：前者用于检查违规，后者用于计算梯度。首版完整保留 ArcRange，包括无穷边界；不要只凭 A/B/C 类型重造合法区间，以免改变测试或未来自定义区间的行为。

### 3.2 每轮变化的数据

| 数组 | 长度 | 谁写、谁读 |
|---|---:|---|
| u_prev | N | 轮开始时保存快照；本轮后续只读 |
| u_current | N | 保存已提交坐标；接受候选后更新，跳跃阶段还会修改 |
| u_trial | N | 每次候选核重写；失败候选可以覆盖 |
| edge_value、edge_derivative | E | 边核写，归约/节点核读 |
| direction、node_energy | N | 节点核写，候选核/归约读 |
| stalled_rounds | E | 停滞计数，取值 0–3，跨轮保留 |
| visibly_moved | N | 节点核计算，用于停滞判断 |
| 归约中间数组及临时空间 | 按算子需要 | 能量求和、最大值、移动数量和违规统计 |
| 层状态、分量统计、错误标志 | 按层/分量 | 接受标记、回溯编号、跳跃计数等 |

推荐从**三个坐标缓冲区**开始。每轮先做一次设备到设备复制，将 u_current 保存到 u_prev。这样即使梯度全部失败、随后发生跳跃，也不会覆盖停滞检测所需的旧坐标。

第一版可以在候选接受后交换 u_current 与 u_trial 的指针；若后续用固定 CUDA Graph，则改为一个提交核将成功候选复制到固定的 u_current 地址，减少图参数管理的复杂度。

显存全部在会话初始化时申请并复用，避免每次迭代、每次回溯申请或释放内存。

首次运行将 u_current 和全部 stalled_rounds 清零；迭代编号为 0 时只评估和显示初态，不执行 step。每轮清空接受标记、跳跃统计和本轮错误状态，但保留停滞计数。旧能量、旧规则能量、largest 使用专用标量位置，不能被失败候选的归约结果覆盖。

## 4. 需要实现哪些核函数和库算子

以下名称是建议名称，**当前仓库尚无这些 CUDA 函数**。首版用“一线程处理一条边”或“一线程处理一个节点”；线程块可先用 256 线程，再比较 128/256 的实际表现。

| 核函数/算子 | 并行粒度 | 主要输入 | 主要输出 | 对应 CPU 逻辑 |
|---|---|---|---|---|
| edgePotentialKernel | 一线程一边 | 坐标、两端、初始距离、类型、阈值 | 惩罚值、导数；可选违规信息 | evaluate 中的边循环 |
| gatherDirectionKernel | 一线程一节点 | u_prev、边导数、CSR、degree、上下界、lambda | direction、节点位移惩罚、方向绝对值 | 梯度累加及方向计算 |
| CUB 求和/最大值归约 | 整层 | 节点惩罚、边惩罚、方向幅度 | 旧能量、规则能量、largest | evaluate/gradientStep 的求和和最大值 |
| trialPositionKernel | 一线程一节点 | u_prev、direction、步长参数、原节点编号、上下界 | u_trial、移动标记、候选节点惩罚 | candidate 循环 |
| edgeEnergyKernel | 一线程一边 | u_trial、静态边信息 | 候选边惩罚 | 无梯度的能量计算 |
| CUB 候选归约 | 整层 | 候选节点/边惩罚、移动标记 | 候选能量、移动数量 | 接受判断所需数据 |
| decideTrialKernel（后续阶段） | 每层一线程 | 两个能量、移动数、attempt/backtrack | 接受标记、下一状态 | 回溯分支 |
| commitTrialKernel（可选） | 一线程一节点 | 接受标记、u_trial | u_current | positions_ 的整体提交 |
| visibleMoveKernel | 一线程一节点 | u_prev、u_current、W | visibly_moved | llround 后的移动比较 |
| stallCounterKernel | 一线程一边 | 两份坐标、可见移动标记、合法区间、旧计数 | 新停滞计数 | repairStalled 的第一个循环 |
| orderedComponentJumpKernel（第二阶段） | 一线程一连通分量 | 当前坐标、停滞计数、分量边列表、CSR | 修复后的坐标/计数、分量跳跃统计 | repairStalled 的第二个循环 |
| finalNodeStatsKernel / finalEdgeStatsKernel | 一线程一节点/边 | 最终坐标、旧坐标、静态图 | 位移、移动数、能量和违规的局部统计 | step 结束统计 |
| CUB 最终统计归约 | 整层 | 局部统计、分量统计 | 一份 OptimizationStats | 各类统计汇总 |
| exportDisplacementKernel（按需） | 一线程一节点 | u_current、W | DBU 单位位移 | displacementDbu |

edgePotentialKernel 与 edgeEnergyKernel 可以共享设备函数，使用模板开关决定是否计算导数；最终边统计也可复用规则和合法区间检查函数。表中列的是职责，不要求每行都单独维护一套公式。

求和、最大值优先采用 CUB DeviceReduce；以后把多层拼成大数组时，可评估 DeviceSegmentedReduce 做“每层一个结果”的分段归约。筛选少量待跳跃边可使用 DeviceSelect，但第一版不需要先做压缩。算子选择依据 [NVIDIA CUB 官方设备级算子目录](https://nvidia.github.io/cccl/unstable/cub/api/device.html)；实际接口以项目选定的 CUDA/CCCL 版本为准。

同一 stream 内可以复用归约临时空间；不同 stream 同时运行时必须使用各自的空间。

## 5. 普通梯度更新：按计算顺序讲清楚

### 5.1 边核：计算距离和导数

边线程先计算第 1.2 节的距离，再调用与 CPU rulePotential 相同的设备函数，输出：

- edge_value[e]：这条边当前的惩罚值。
- edge_derivative[e]：惩罚对**归一化距离**的导数，暂不乘 lambda。

规则必须完整保留：

| 类型 | 使用的惩罚 |
|---|---|
| A | 距离低于阈值时，用“距离减阈值”的平方 |
| B | 距离为负时用距离平方；非负时用零到阈值之间的 bump |
| C | 根据距离正负，在负阈值到零、或零到正阈值之间使用 bump |

对于 bump：

$$
z=\frac{d-a}{b-a},\qquad
\phi(d)=16z^2(1-z)^2,\qquad
\phi'(d)=\frac{32z(1-z)(1-2z)}{b-a}.
$$

- $d$：当前这条边的归一化距离。
- $a,b$：bump 所在区间的左右端点，与 d 单位相同。
- $z$：距离在区间中的相对位置；不是 trim 坐标。
- $\phi(d)$：规则惩罚值。
- $\phi'(d)$：惩罚值随距离变化的速度，即需要的导数。

这些表达式仅用于 a < d < b；到边界或区间外时，bump 的值和导数都为零。注意：区间中点的导数也为零，但惩罚值并不为零，这正是需要扰动和停滞跳跃的原因。

源码：[Optimizer.cpp](../src/optimize/Optimizer.cpp)，bump、lowerBound、rulePotential，第 15–42 行。

### 5.2 节点核：将多条边的影响合起来

$$
g_i=
0.01\,\frac{u_i}{\sqrt{u_i^2+0.01^2}}
+\lambda\sum_{e\text{ 连接 }i}\sigma_{i,e}\,\phi'_e(d_e).
$$

- $g_i$：节点 i 的总梯度，对应归一化位移 u 的梯度。
- $u_i$：本轮开始的累计归一化位移，从 u_prev 读取。
- 第一项：限制不必要位移的梯度，避免只顾满足边规则而移动过远。
- $\lambda$：当前轮规则惩罚的权重；当前调度为第 1–25 轮取 10，第 26–50 轮取 20，第 51–75 轮取 40，此后取 80。
- 求和：遍历节点 i 的所有关联边。
- $\sigma_{i,e}$：若节点 i 是边 e 的 src 则为 −1，是 dst 则为 +1。
- $\phi'_e(d_e)$：前一个边核算出的导数。

直观上，一条边要求距离变大时，起点倾向往左、终点倾向往右；同一 trim 连着多条边，就必须把这些要求一起考虑。

实现时，每个节点线程先按 CPU 写法计算正则梯度，再按 CSR 中的原边顺序逐项加减 lambda × 导数。不要先对导数求和再乘 lambda，否则会额外改变浮点运算顺序。平方根部分首版保持 CPU 的 hypot 表达方式。

**推荐 CSR 汇总，而不是让边线程 atomicAdd 到节点梯度。** 两者在实数运算上相同，但原子浮点累加顺序可能变化，节点连接很多边时还会竞争。CSR 方案让一个线程独占一个节点的梯度，便于与 CPU 对照。普通归约仍可能带来浮点差异，见第 10 节。

源码：[Optimizer.cpp](../src/optimize/Optimizer.cpp)，evaluate，第 97–117 行。

### 5.3 节点核得到方向；整层归约决定公共缩放

$$
v_i=\operatorname{clamp}\left(-\frac{g_i}{q_i},\,L_i-u_i,\,U_i-u_i\right),
\qquad
M=\max_i|v_i|,
\qquad
s=
\begin{cases}
h/M,&M>h,\\
1,&M\le h.
\end{cases}
$$

- $v_i$：节点 i 的初步移动方向和幅度，尚未成为实际位移。
- $q_i$：degree[i]，即 1 加关联边数；连接越多，分到的移动通常越小。
- $L_i,U_i$：该节点允许的累计位移下界、上界。
- $\operatorname{clamp}(z,l,r)$：把 z 限制在 l 到 r 之间。
- $M$：**这一层全部节点**的最大方向幅度。
- $h$：最大梯度步长，单位为 W，对应 max_step_w。
- $s$：整层公共缩放因子；最大方向过大时整体缩小，M 等于零时取 1。
- $g_i,u_i$：该节点的总梯度、本轮开始位移，与上一节相同。

先限制方向，再做公共缩放，是现有代码的顺序。不能给每个节点或连通分量分别算 s；那会改变当前算法。

源码：[Optimizer.cpp](../src/optimize/Optimizer.cpp)，gradientStep，第 155–162 行。

### 5.4 候选核同时生成所有下一位置

$$
u_i^{\mathrm{trial}}
=\operatorname{clamp}\left(
u_i+\operatorname{clamp}\left(s\,2^{-b}(v_i+j_{i,a}),-h,h\right),
L_i,U_i
\right).
$$

- $u_i^{\mathrm{trial}}$：这次试探得到的候选位置；上标 trial 是标签，不是次方。
- $u_i$：本轮开始位置，从 u_prev 读取。
- $a$：扰动尝试编号，依次为 0、1、2。
- $b$：本次扰动下的回溯编号，从 0 到 19；这里 $2^{-b}$ 才是次方，表示每次减半。
- $j_{i,a}$：扰动值。a 为零时为零；否则原层内编号 i 加 a 为偶数时取 +0.01，为奇数时取 −0.01。
- $v_i,s,h,L_i,U_i$：依次为初步方向、整层缩放、最大步长、允许位移下界和上界，与上一步相同。

本节 a、b 是循环编号，与第 5.1 节 bump 公式中的区间端点不是同一变量。这种记法直接对应代码中的 attempt、backtrack；实现时应使用这些完整名称。

这个公式只是“旧位置加移动量”，两次 clamp 分别限制单次梯度步长和最终允许位置。

候选核每个线程只写自己的 u_trial[i]。没有线程在此时修改 u_prev，也不提交 u_current。

### 5.5 能量归约：整层一起决定接受还是重试

$$
E(u)=
\sum_i0.01\left(\sqrt{u_i^2+0.01^2}-0.01\right)
+\lambda\sum_e\phi_e(d_e(u)).
$$

- $u$：这一层全部节点的位移数组，可以是旧数组或候选数组。
- $E(u)$：整层总能量。
- 第一个求和：所有节点的位移惩罚；i 遍历节点，$u_i$ 是节点 i 的累计归一化位移。
- 第二个求和：所有边的规则惩罚；e 遍历边。
- $d_e(u)$：用数组 u 中两个端点的位移计算的边距离。
- $\lambda,\phi_e$：当前轮规则权重和该边的惩罚函数。

GPU 分别求节点项之和、边项之和，最后按“节点和 + lambda × 边和”组合，保持 CPU 的计算结构。

接受条件：

$$
E_{\mathrm{trial}}<E_{\mathrm{old}}-10^{-12}\max(1,E_{\mathrm{old}}).
$$

- $E_{\mathrm{trial}}$：候选数组的总能量。
- $E_{\mathrm{old}}$：本轮开始时、使用同一个 lambda 计算的总能量。
- $10^{-12}\max(1,E_{\mathrm{old}})$：源码要求的最小能量下降量；max 表示取较大值。

满足条件则全层接受，否则继续回溯。以下细节不能省略：

1. 候选移动数量按绝对位移变化大于 1e−12 判断。
2. 如果移动数量为零，只退出当前扰动的回溯循环；仍可能进入下一个扰动尝试。
3. 若旧规则能量恰好为零，第一次尝试结束后不再做扰动。
4. 最多尝试 3 × 20 个候选；实际次数往往更少，需要采样测量。
5. 全部失败则保持旧坐标，接着做停滞处理。
6. lambda 变化后，必须重新计算旧能量；不能直接拿上一轮不同 lambda 下的能量比较。

首版由 CPU 读回少量标量控制 attempt、backtrack，流程最容易验证。后续将接受判断移入 decideTrialKernel，减少 CPU/GPU 往返。

源码：[Optimizer.cpp](../src/optimize/Optimizer.cpp)，第 166–200 行；lambda 调度见 [RunOptimization.cpp](../src/optimize/RunOptimization.cpp)，第 241–243 行。

设两个 trim 只有一条 B 边，原始 x 为 100、140 DBU，W 为 10 DBU，两端 u 均为零，阈值为 5，lambda 为 10，h 为 0.1。假设两端允许的归一化位移范围都为 [−20,20]，因此本例不会被移动域额外限幅。

## 6. “同步更新”到底如何实现

### 6.1 同一阶段内并行，阶段之间按 stream 顺序执行

边核必须全部完成，节点汇总核才能读取完整的导数；归约得到 s 后，候选核才能使用 s。首版把这一层的相关核和 CUB 算子放进**同一个显式 CUDA stream**。

同一 stream 中的操作按序执行；普通核中的 __syncthreads() 只同步一个线程块，不能让整个 grid 的节点和边共同等待。因此不能把“全部边算完 → 全部节点更新”随意塞进一个普通核，靠 __syncthreads() 解决。参见 [NVIDIA CUDA 编程指南：线程层级与 streams](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-c-programming-guide/index.html#streams)。

| 数据依赖 | 同步方式 |
|---|---|
| 边导数 → 节点梯度 | 同一 stream 中顺序提交两个核 |
| 最大值归约 → 候选坐标 | 同一 stream；候选核读取设备端归约结果 |
| 候选坐标 → 候选能量 | 同一 stream |
| 候选接受 → 正式坐标提交 | CPU 读回结果后提交，或设备判断核后执行提交核 |
| 全部停滞计数完成 → 跳跃 | 同一 stream 中两个独立核 |
| 最终坐标 → CPU 显示/后处理 | 异步复制到固定页内存，等待对应 event/stream 完成 |
| 不同 stream 之间共享结果 | 显式 event 记录和等待 |

不需要每个核后调用 cudaDeviceSynchronize。CPU 真正需要读取结果时，等待对应 stream 或 event；多层同时运行时，这也避免阻塞无关层。相应同步 API 的语义见 [CUDA 官方显式同步说明](https://docs.nvidia.com/cuda/archive/13.0.0/cuda-c-programming-guide/index.html#explicit-synchronization)。

### 6.2 两条边共享一个 trim 时怎么办

例如边 A–B、B–C 都影响 B：

1. 两个边线程只读取旧坐标，分别写自己的导数。
2. B 对应的唯一节点线程读取两条导数，得到 B 的总梯度。
3. B 对应的唯一候选线程写 u_trial[B]。

因此正常梯度阶段没有两个线程同时写 B 的坐标，也不需要对坐标做 atomicAdd。

### 6.3 多层并行时仍然分别接受候选

可以让 M2、M3 等层使用不同 stream，但每层保留自己的能量、largest、回溯状态和工作区。某层接受第一个候选，不代表其他层也接受。

第一版先用单 stream 顺序处理各层。确认正确且发现小核开销后，再比较“每层一个 stream”和“多层拼接加分段归约”。每轮报告前等待各层完成，并按原层顺序汇总。小层是否回退 CPU 应由性能测量决定。

## 7. 停滞检测和跳跃：最需要单独设计的部分

### 7.1 停滞计数可以完全并行

visibleMoveKernel 对每个节点比较：

$$
\operatorname{llround}(W u_i^{\mathrm{current}})
\ne
\operatorname{llround}(W u_i^{\mathrm{prev}}).
$$

- $i$：当前节点编号。
- $u_i^{\mathrm{prev}}$：本轮开始的累计位移。
- $u_i^{\mathrm{current}}$：梯度尝试结束后的累计位移，尚未跳跃。
- 上标 prev、current：坐标版本标签，不是次方。
- $W$：把归一化位移还原成 DBU 的线宽。
- llround：按最近整数取整，恰好半整数时远离零。
- 不等号：表示显示层面的整数 DBU 位移发生变化。

这里比较的是**两份累计位移分别取整后的结果**，不能先相减再取整；也不能用默认的“半整数取偶数”的转换代替 llround。

随后每个边线程检查：两端都没有可见移动，并且旧位置和梯度结束位置都达到修复容差的违规标准，才把这条边的计数加一，最大为 3；否则清零。违规标准保持 gap > 0 且 gap × W ≥ 修复容差。gap 是距离到所有合法区间的最小间隔。

**所有边的计数都算完，才能开始跳跃。** 否则后面的边可能误用跳跃后的坐标来判断这一轮是否停滞。

源码：[StallRepair.cpp](../src/optimize/StallRepair.cpp)，arcViolated 第 14–29 行、repairStalled 第 115–131 行。

### 7.2 为什么不能直接“一条边一个线程，同时跳跃”

当前 CPU 按边的原顺序处理计数达到 3 的边。一次成功跳跃会：

1. 同时修改这条边的两个端点。
2. 对实际发生位移的端点，将其所有关联边的停滞计数清零。
3. 后面的边读取已经变化的坐标和计数，再决定是否还能跳。

如果 A–B 和 B–C 同时跳，两个线程都可能修改 B；即使给 B 加锁，也不保证谁先处理，仍会改变当前结果。

跳跃还有两个容易误改的性质：它不受普通梯度 h 的限制，也没有“整层能量必须下降”的接受条件。给它额外加这些条件，会改变现有算法。

### 7.3 第一阶段：CPU 有序跳跃，作为对照版本

先将梯度和停滞计数放到 GPU；检测出至少一条计数达到 3 的边时，读回当前坐标和计数，在 CPU 按原顺序执行跳跃部分，再上传结果。

为此，应把现有 repairStalled 拆成“更新计数”和“按序尝试跳跃”两个内部步骤；不要读回后调用整个 repairStalled，把计数再加一次。

这是验证阶段方案。全量读回坐标和计数可能消耗明显时间，必须计入 GPU 版本耗时；不能只统计核时间。没有候选跳跃时跳过该传输。

### 7.4 第二阶段：连通分量之间并行，分量内部保留原顺序

更适合作为最终实现的方案：

1. CPU 初始化时，按**全部约束边**计算图的无向连通分量。
2. 每个分量保存自己的边列表，并按原边编号排序。
3. orderedComponentJumpKernel 中，一个线程负责一个分量。
4. 该线程按列表顺序执行与 CPU 相同的跳跃判断、双端点提交和计数清零。
5. 不同分量之间同时执行；所有分量结束后再开始最终统计。

为什么这种并行不会引入边顺序冲突：不同连通分量没有共享节点，也没有跨分量的关联边；一个分量里的坐标修改和计数清零不会影响另一个分量。因此只需保持**每个分量内部**的原执行顺序，不必保持不同分量之间的交错顺序。

每个线程写自己的分量统计，最后归约，避免多个线程同时写全局计数。孤立节点没有跳跃工作，可不加入该任务列表。

现有样例汇总为 85,069 个连通分量，但这个总数包含孤立节点，**不能直接当作 85,069 个有效并行任务**。实施前需统计有边分量数量、最大分量边数和每轮活跃分量分布。一个很大的分量仍然串行，可能成为尾部耗时。

这一方案是在保持状态依赖的前提下减少 CPU 往返，并不保证单个分量在 GPU 上比 CPU 快。若大分量成为瓶颈，再单独评估混合调度。用图着色或匹配来同时跳跃的方案需要重新验证算法行为，放在后续研究阶段。

### 7.5 设备跳跃函数要逐项移植的规则

从 [StallRepair.cpp](../src/optimize/StallRepair.cpp) 的 jumpAcrossBarrier，第 32–108 行移植：

- 只对 B 的正距离禁区和 C 的非零禁区尝试跨越；A 和负距离 B 不适用。
- 目标在禁区中点另一侧，加上归一化跳跃偏移。偏移由 nm、DBU/微米和线宽换算，不能直接使用 nm 数值。
- 恰在中点时先试增大距离，无法实现时才试反方向；不在中点时只试规定方向。
- 先检查两端移动域提供的容量，再按 degree 的阻力比例分配位移。
- 保留原来的浮点舍入容差、最终距离校验、严格跨过中点和有限值检查。
- 两端都通过检查后才能提交，不能只修改一端。
- 只给真正移动的端点清空关联边计数；另一个未动端点不自动清空。
- 遍历下一条边时重新读取停滞计数，不能只信预先生成的候选列表。
- stall_repaired 统计的是成功跳跃次数，不代表已经满足合法区间。

## 8. 控制流程伪代码与减少同步的路线

下面是第一版的逻辑伪代码，省略 CUDA 错误检查和资源管理；不是可以直接编译的实现。

~~~cpp
stepLayer(lambda):
    copy_device(u_current, u_prev)  // source -> destination

    edgePotentialKernel(u_prev)
    gatherDirectionKernel(u_prev, edge_derivative, lambda)
    reduce_old_energy_rule_energy_and_largest()
    // 后续核直接读设备端 largest 来求 scale。

    accepted = false
    for attempt in [0, 1, 2]:
        for backtrack in [0, ..., 19]:
            trialPositionKernel(u_prev, direction, attempt, backtrack)
            reduce_moved_count()
            moved = download_scalar_and_wait()
            if moved == 0:
                break

            edgeEnergyKernel(u_trial)
            reduce_trial_energy()
            trial_summary = download_scalar_and_wait()
            if sufficiently_lower_energy(trial_summary):
                swap(u_current, u_trial)
                accepted = true
                break

        if accepted or old_rule_energy == 0:
            break

    visibleMoveKernel(u_prev, u_current)
    stallCounterKernel(u_prev, u_current)

    // 阶段一：有候选时传回 CPU，按原序跳跃，再上传。
    // 阶段二：用下面的设备核替代该 CPU 路径。
    orderedComponentJumpKernel(u_current, stalled_rounds)

    finalNodeStatsKernel(u_prev, u_current)
    finalEdgeStatsKernel(u_current, lambda)
    reduce_final_statistics()
    return download_small_statistics_and_wait()
~~~

第一版为了容易比对，候选移动数和候选能量各有一次主机等待。旧能量和旧规则能量也需要在第一次判定前读回，可与首次标量传输合并。它们是需要测量的开销，而不是理想性能版本。

按下面顺序减少等待：

1. 将“没有移动就跳过能量评估”的判定留在 GPU。候选能量核读取设备端 moved，明确写入无工作状态，避免使用上次残留的归约结果；CPU 每个候选只读回一次汇总。
2. 用 decideTrialKernel 管理 attempt、backtrack、accepted，固定地址的 commitTrialKernel 提交结果。
3. 如果 profile 显示核启动和主机等待占比高，再评估 CUDA Graph。先捕获一次候选计算链，随后再研究设备条件控制的整轮图。

不能简单说“用 Graph 就不需要同步了”：只捕获一次候选链，CPU 仍然要决定是否继续。使用条件节点取决于选定 CUDA 版本；固定展开 60 次再用 active 标志跳过，也有多余启动开销。两者都要测量后选择。

设备状态控制版必须保证：一旦接受候选，后续候选槽位不再修改该层坐标；moved 为零时跳到下一次扰动，而不是整轮结束；旧规则能量为零时关闭后续扰动。每轮状态重置后才能再次使用这条执行链。

不建议第一版写一个长期驻留的大核，在线程块之间用自旋等待模拟全局屏障；正常的多核依赖已经能表达这个算法。

最终统计以跳跃后的 u_current 为准：moved 和 max_step_dbu 比较的是它与 u_prev 的净变化，不是梯度位移和跳跃位移各自绝对值的和。accepted 在梯度接受或至少一次跳跃成功时为真；跳跃成功后重新计算能量及违规统计。max_repair_dbu 单独记录单次成功跳跃的最大端点位移。

## 9. 哪些工作可以省，哪些不能直接删除

### 9.1 优先消除的重复工作

| 当前重复工作或迁移风险 | 建议改造 | 原因 |
|---|---|---|
| 每次边评估重新计算原始距离、归一化阈值 | 初始化预计算 | 图、原始坐标、线宽在会话内固定 |
| 每次 gradientStep 创建多个 vector | 常驻设备数组和可复用 CPU 工作区 | 避免反复分配 |
| 每个失败候选都算完整违规/位移统计 | 增加 energy-only 路径 | 接受判断只需要移动数和能量 |
| 每次边判断重复换算合法区间边界 | 初始化归一化并扁平存储 | 减少重复算术和间接访问 |
| 无显示需求也每轮获取全部位移 | 将统计与坐标快照接口分开 | 减少设备到主机复制 |
| 迁移时误把静态图和邻接关系放进每轮重建 | 保持初始化一次 | 当前算法的边和移动域在迭代中固定 |

RunOptimization.cpp 当前每轮都会调用 displacementDbu，即使没有实际绘制需求。CUDA 后端必须改这个接口，否则计算搬到 GPU 后仍然每轮把整套坐标拉回来。

GUI 单步模式每步仍应取得完整快照；连续模式可以配置显示间隔，但要继续处理 GUI 事件和停止请求。最终导出残差、位移和进入后处理前必须取得最新完整坐标。

### 9.2 不能以“加速”为由静默省略的逻辑

- 不能删除 degree 中的加一，或因为某个节点不能动就修改其他节点的 degree。
- 不能删除扰动、回溯、能量下降门槛、位移惩罚和停滞跳跃。
- 不能因为 blocked 节点不动，就把它连接到可动节点的边删除。
- 固定端点边即使对位置更新没有贡献，能量常数仍会影响相对接受门槛；若压缩这些边，需要保留相应常数及统计/停滞行为。
- 不能把“违规小于容差”直接等价为“规则惩罚为零”。
- 不能将各连通分量独立做梯度回溯；当前公共缩放和接受条件是整层的。
- 不能把连续位移直接当整数合法化结果。

这些是算法约束，不是 CUDA 本身的要求。要改变它们，应作为另一个算法版本评估。

## 10. 数值一致性与正确性验证

第一版全部采用 double，不启用 fast-math。距离、上下界、lambda、导数、能量和回溯比较都保留 FP64。

GPU 并行求和的结合顺序与 CPU 顺序循环不同；数学等价不保证逐位一致。接受门槛很小，差异可能改变回溯次数，继而影响之后的轨迹。因此“没有数据竞争”与“每轮完全一样”必须分别验证。

建议按以下层次验收：

| 层次 | 必须比较的结果 |
|---|---|
| 单条边 | 距离、惩罚、导数、合法区间 gap；覆盖 A/B/C 的边界、中点、负距离 |
| 单节点 | CSR 累加、degree、上下界投影、blocked 节点、原编号扰动 |
| 一次候选 | 每个坐标、moved、最大方向、旧/新能量、接受条件左右两侧 |
| 一轮 | attempt/backtrack、接受标志、梯度后坐标、停滞计数、跳跃顺序及最终坐标 |
| 多轮 | 每轮 CSV 指标、残差、总位移、最后送入后处理的坐标 |
| 完整流程 | 后处理的最终冲突数和位移质量、GUI/单步/停止/数据库销毁行为 |

专门构造以下边界用例：没有边、没有节点、只有一个节点、两端都固定、高度数节点、所有候选失败、moved 为零、扰动才成功、lambda 换挡、±0.5 DBU 舍入、连续三轮停滞、两条跳跃边共享端点、不同分量同时跳跃、容量恰好可行、只有反方向跳跃可行、自定义 ArcRange。

复用 [OptimizerTest.cpp](../test/OptimizerTest.cpp) 的现有 CPU 用例，增加 CPU/GPU 差分测试。数值容差应按距离/梯度/能量的量级分别设定，并检查离接受门槛还有多远，不能用一个宽松坐标误差掩盖不同分支。

若必须做到严格复现，先提供诊断模式：固定归约树，检查乘加收缩和中间表达式，必要时用 CPU 原顺序评估临界候选。它会牺牲性能；不能提前承诺跨 CPU/GPU、跨显卡逐位一致。

启动错误用 CUDA 错误检查及时捕获；非有限能量通过设备状态返回主机并按现有行为报错。使用 Compute Sanitizer 检查越界和同步问题，并单独审查全局内存写入所有权；工具检查不能替代顺序依赖分析。

## 11. 预期时间开销：应当测什么

### 11.1 每轮开销取决于回溯，不只是节点数

设 N 为节点数、E 为边数、R 为这一轮实际评估的候选数：

- 旧能量与梯度：遍历节点和边，CSR 读取约 2E 个关联项。
- 每个候选：遍历 N 个节点和 E 条边，再归约。
- 停滞检测与最终统计：再遍历节点和边。
- 有序跳跃：包括扫描边以及成功移动端点的关联边计数清零，受分量大小分布影响。

所以常规并行部分总体约为 **O((1+R) × (N+E))**；还要加上跳跃、核启动、标量等待和数据传输。核中单条边的算术很短，显存访问与调度开销可能比浮点运算更重要。

已有样例有 328,756 个节点、431,308 条边，平均每节点约 2.62 个关联项，适合从一线程一节点的 CSR 汇总开始。所有 double 数组、邻接表、区间和归约工作区的显存量级预计为数十到数百 MB，应在实现时按实际数组和 CUB 临时空间精确统计。

一次全部节点 double 坐标约 2.63 MB。容量不大，但频繁同步和传输会损失收益；若再传回全部计数和重复上传，开销进一步增加。

### 11.2 使用已有日志估计整套 DEL 的收益上限

下表来自 [已提取的运行指标](runtime_analysis_metrics.json)，不是 GPU 测试，也不保证代表其他设计。

| 阶段 | 已有 CPU 日志耗时 |
|---|---:|
| 建图 | 2.017 秒 |
| 连续迭代阶段 | 40.173 秒 |
| 后处理 | 188.594 秒 |
| DEL 总时间 | 234.489 秒 |

该样例连续阶段占总时间约 17.13%，后处理占约 80.43%。保持其他耗时不变，即使**整个连续阶段**加速 10 倍，总体也只有约 **1.18 倍**；即使连续阶段耗时趋近于零，总体上限也只有约 **1.21 倍**。

这还是把整个连续阶段都当成可加速部分的乐观计算；其中日志、GUI 等开销并不一定随 CUDA 加速。若主要关心交互式每轮更新时间，CUDA 仍可能很有价值；若关心 DEL 从头到尾的总耗时，需要另开后处理优化工作。

首版保持 [Postprocess.cpp](../src/optimize/Postprocess.cpp) 的 CPU 求解路径，连续迭代结束后一次性传回坐标。当前后处理的连续位移收缩和整数合法化涉及 LP/MIP 求解，不能用本计划中的梯度核直接替代。

### 11.3 必须新增的性能记录

1. 每层每轮的 N、E、实际候选数、扰动次数、接受步长。
2. 旧梯度、候选评估、归约、停滞检测、跳跃、最终统计分别耗时。
3. CPU 等 GPU 的时间、每轮复制字节数、完整坐标快照次数。
4. 跳跃候选数、成功数、活跃分量数、最大活跃分量边数。
5. 分开报告：纯设备计算、连续阶段端到端、整套 DEL 端到端。

使用 CUDA events 测设备阶段，用 CPU 时钟测真实端到端；比较时保持迭代数、输入、参数、显示/日志配置一致。预热后的重复运行报告中位数和波动，同时单列初始化和首次运行成本。先用 Nsight Systems 找等待和传输，再按需要用 Nsight Compute 分析具体核。

不要在没有回溯次数、分量分布和端到端测量前承诺 10 倍或 100 倍加速。

## 12. 建议的文件和接口改造

下面是建议结构，不是当前已有文件：

| 文件 | 主要职责 |
|---|---|
| include/del/CudaOptimizer.h | 主机侧 CUDA 后端接口，隐藏 CUDA 实现细节 |
| src/optimize/cuda/CudaGraphData.h/.cpp | 扁平化节点、边、CSR、合法区间、连通分量 |
| src/optimize/cuda/CudaOptimizer.cu | stream、显存、归约工作区、迭代调度、快照导出 |
| src/optimize/cuda/Potential.cuh | 与 CPU 一致的距离、规则惩罚、导数、区间 gap 设备函数 |
| src/optimize/cuda/GradientKernels.cu | 边评估、节点汇总、候选生成、接受/提交 |
| src/optimize/cuda/StallKernels.cu | 可见移动、停滞计数、有序分量跳跃 |
| src/optimize/cuda/StatsKernels.cu | 统计和 DBU 位移导出 |
| test/CudaOptimizerTest.cpp | CPU/GPU 差分及状态转移测试 |

集成位置：

- [Optimizer.h](../include/del/Optimizer.h)：保留 CPU 后端作为参考；整理公共配置、统计和坐标快照接口。
- [RunOptimization.cpp](../src/optimize/RunOptimization.cpp)：把目前固定的 vector<LayerOptimizer> 调用改为后端适配，分离 step/evaluate 与下载坐标。保持 lambda、迭代上限和单步语义。
- [ResidualReport.h](../src/optimize/ResidualReport.h)：检查当前对 LayerOptimizer 的依赖，改为接受主机快照或只读访问接口，避免报告函数迫使每轮回传。
- [CMakeLists.txt](../CMakeLists.txt)：增加默认关闭的 DEL_ENABLE_CUDA 选项，按需检测/启用 CUDA 和链接 CUDA::cudart；架构由构建配置或探测结果决定，不写死显卡型号。
- [BUILD](../BUILD) 和 [test/BUILD](../test/BUILD)：保持已有 CPU 构建可用；若交付要求支持 Bazel GPU 构建，补齐对应 CUDA 目标及条件，而不是只修改 CMake。

CUDA 编译单元尽量只接收普通数值数组，不引入 OpenDB、SWIG、GUI 头文件。会话对象管理设备资源；数据库释放或用户停止时，先结束相关异步任务，再销毁缓冲区。GPU 工作线程不直接操作数据库和 GUI。

后端选择建议提供 cpu/cuda/auto。未编译 CUDA 或无设备时，auto 可以回退 CPU；显式指定 cuda 失败时应说明原因。执行中出错不能静默拿陈旧 CPU 状态继续跑。

## 13. 分阶段实施与交付标准

| 阶段 | 做什么 | 完成标准 |
|---|---|---|
| P0：建立基线 | 记录回溯次数、分量分布；拆出 energy-only 与有序跳跃内部函数；确定工具链 | CPU 行为对照通过，有阶段耗时数据 |
| P1：GPU 梯度迭代 | 扁平数据、三个坐标缓冲、边核、CSR 汇总、候选/归约；GPU 停滞计数、CPU 控制回溯和有序跳跃 | 单轮/多轮差分通过，能完成已有样例，报告含传输的实际耗时 |
| P2：GPU 常驻状态 | 有序分量跳跃、最终统计；坐标按需下载 | 常规轮无需完整坐标回传；共享端点和计数清零用例通过 |
| P3：减少调度开销 | 合并安全的节点操作、减少标量等待；比较多层 streams、分段归约、CUDA Graph | 用相同工作负载证明端到端收益，并保留较简单方案的对照 |
| P4：独立算法实验 | 原子累加、混合精度、并行冲突跳跃等 | 明确算法/数值变化，比较残差、位移、迭代数和后处理成本 |

每阶段都保留 CPU 参考路径和可关闭的 GPU 后端。P1 首先回答“能否正确执行”，P2 回答“能否避免每轮回传”，P3 才针对实际瓶颈调优。P4 不作为第一版交付的前提。

第一批最值得写的计算核是 **edgePotentialKernel、gatherDirectionKernel、trialPositionKernel、edgeEnergyKernel**，配合 CUB 归约先跑通一轮。然后补齐停滞、跳跃和统计，才能称为完整的 trim 迭代 CUDA 后端。
